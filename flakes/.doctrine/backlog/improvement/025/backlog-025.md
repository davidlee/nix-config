# IMP-025: Set load-prefer-newer for every Emacs, batch included, via site-start

Raised 2026-10-16 (from satan IMP-035).

## Problem

`~/dev/satan/satan/*.elc` are built deliberately at Emacs startup by
`dl-satan--compile-stale` (`~/.config/emacs/apps/dl-satan.el`, perf: interpreted
timers stall input). Interactive Emacs sets `load-prefer-newer`
(`core/dl-core.el`, twice; `core/dl-compile.el`) and `just test` sets it in
`dev/satan-test.el`. But an agent's ad-hoc `emacs --batch -L ./satan …` loads
no init, so `require` takes the stale `.elc` over a freshly edited `.el` and
the agent tests old code. Agents will keep doing this; a just recipe they
must remember does not fix it.

## Fix shape

`site-start.el` is loaded in batch too (not under `-Q` / `--no-site-file`), so
`(setq load-prefer-newer t)` there covers every non-`-Q` invocation.

Where it lives under nixpkgs `emacsWithPackages` (checked 2026-10-16):

```
bin/emacs (wrapper, sets EMACSLOADPATH)
  └─ emacs-packages-deps/share/emacs/site-lisp/site-start.el   ← generated by wrapper.nix
       └─ load <emacs>/share/emacs/site-lisp/site-start          ← base package (NIX_PROFILES paths)
```

There is no `site-start.d/` hook in either file.

- Patch the base emacs's `site-start.el` via `overrideAttrs` — simple, but it
  forces a from-source Emacs rebuild (`emacs/emacs.nix` already does this for
  the Darwin macport only).
- Preferred, if possible: override the cheap derivation that generates the
  wrapper `site-start.el` (emacs-packages-deps / wrapper.nix) to append the
  setq — no Emacs rebuild. Verify which derivation writes it.
- Do NOT shadow `site-start` via an earlier `EMACSLOADPATH` entry: only the
  first `site-start` on the path loads, so it would drop nix's.

## Done when

`emacs --batch --eval '(princ load-prefer-newer)'` prints `t`. Then drop the
redundant second `load-prefer-newer` in `~/.config/emacs/core/dl-core.el`.
`-Q` runs stay uncovered by design.
