# ADR-003: System and home keep separate lifecycles and pins

## Context

On every platform, Home Manager is a standalone configuration
(`homeConfigurations."david@<host>"`), not a NixOS module. It uses its own
nixpkgs input (`nixpkgs-home`), updated more aggressively than the system's
`nixpkgs`, and activates with `just home-switch` (no sudo, fast). `stable` is
an escape hatch for packages broken on unstable. Darwin embedded Home
Manager as a darwin module until SL-004 (DEC-017).

Frameworks considered so far (nixos-unified, Den) tend to embed Home Manager
in the system evaluation or share one nixpkgs. nixos-unified was rejected
partly for that reason (RFC-001, "Considered and not adopted:
srid/nixos-unified").

## Decision

We will keep the system evaluation (NixOS or nix-darwin) and Home Manager
separate on every platform, with separate nixpkgs pins and separate
activation. Feature colocation (ADR-002)
is a source-layout concern only; it does not merge evaluations, pins or
activation cycles.

## Consequences

### Positive

- Userland breakage is fixed and rolled out without a system rebuild.
- System infrastructure updates conservatively.

### Negative

- System and home cannot read each other's config; any cross-boundary
  dependency (e.g. home services needing a system PostgreSQL) must be checked
  by the outer resolver (ADR-001), and only as intent.
- The two halves of one feature can be activated at different times.

### Neutral

- Any future composition library must respect this boundary.

## Verification

- `hosts.nix` produces separate `nixosConfigurations`,
  `darwinConfigurations` and `homeConfigurations` outputs; the
  derivation-identity gate covers all three.
