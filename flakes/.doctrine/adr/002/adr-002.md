# ADR-002: Features are plain data addressed by attribute path

## Context

Modules are organised by evaluation class today (`modules/nixos/`,
`modules/home/{shared,linux}/`, `darwin/`), so one capability (snooze, sway,
capsule) is split across directories and joined only by a flag name.

REFACTOR.md (completed) removed an earlier setup in which every leaf was a
flake-parts module, auto-discovered by `import-tree`, registering itself as
`flake.homeModules.<name>` / `nixosModules`. Its reasons:

| Removed | Reason |
|---|---|
| leaf files as flake-parts modules | two evaluator domains conflated in one tree; ceremony for local-only modules |
| `import-tree` auto-discovery | a "magic directory" rule plus a flake input |
| `flake.*Modules` exports | indirection with one internal consumer |
| `cliPackages` option matrix | options with zero consumers |

That history rejects Den's plumbing (auto-discovery, outputs, flake-parts as
the carrier). It does not reject Den's shape: one identity for a capability
across classes. A precedent for the shape already exists:
`modules/shared/cli/_packages/*.nix` return `{common, linuxHome,
linuxSystem}` from one file per category.

Module merge order matters: list options merge in reversed breadth-first
import order (`mem.fact.nix.merge-order`), so moving or reordering imports changes
derivations.

## Decision

1. **Shape.** A feature is plain data:
   `{ name; nixos?; homeManager?; darwin?; requires?; }`. `name` is
   required and is the feature's identity. Each class value is an ordinary
   module, written inline by convention (a path is accepted and never read
   during resolution). `requires` is an optional list of `"<area>.<name>"`
   prerequisites (ADR-001 D4). No other key is allowed: a misspelt class
   key would otherwise drop that half silently. A feature value is never
   itself a module of any evaluator.
2. **Addressing.** Features are referenced by attribute path
   (`desktop.niri`), never by file path. The tree is two levels deep,
   `<area>.<name>`. `features/default.nix` lists the areas as written
   `{ name; value; }` pairs; each area is one file, `features/<area>.nix`,
   a written list of self-named features. Area and feature names must be
   non-empty and may not contain `.`, since paths are dot-joined.
3. **Granularity.** A feature's halves stay together, never split by
   platform. A feature moves to its own file, `features/<area>/<name>.nix`,
   listed in its area as `(import ./<area>/<name>.nix)`, when it would
   dominate the area file (about 100 lines prompts the judgement; it is not
   a rule). The own file holds the whole record. A record too big for one
   file may import modules of its own from `features/<area>/<name>/`,
   listed explicitly in the half that uses them (D7: no discovery); they
   belong to that record and to no other. Assets sit near their
   feature. Moving a feature between files touches no host, profile or
   other feature; relative paths inside it may change.
4. **Exclusion boundary.** Descriptors (feature records, their `enable`
   options, outer settings schemas) may be evaluated for every host.
   Unselected class implementations and their package expressions are
   never forced by resolution or projection. This isolates evaluation
   failures (missing package attributes, removed options, `throw`). It does
   not isolate parse errors in a file holding descriptors; `nix fmt` parses
   every file before evaluation. Resolver code must not traverse into
   implementation values; testing attribute presence is fine. Structural
   checks read every record, selected or not, and fail every host: each
   area and feature is a record (a path listed where `(import …)` was meant
   is named as such); `name` is a non-empty, dot-free string; `requires` is
   a list of strings naming existing features; descriptor keys are known;
   no names repeat; no option is declared at a feature's path. The resolver
   reads only key names, `name`, `requires`, option declarations and the
   position of `name`; none forces a class value, so the boundary holds.
5. **Projection order.** Selected features project in list order (areas,
   then the features of each), never `attrNames` order. Migration preserves
   existing order. No numeric priorities without a concrete need.
6. **Identity.** One selected entry per feature path, so duplicates cannot
   arise from selection. `_file` is set for error provenance only, as
   `"<flake-relative file>:<line> (<area>.<name>#<class>)"`, from the
   position of `name`. The location is relative, for readability, and only
   for records written in this flake (a record from elsewhere keeps its
   absolute path). Records are written literally by convention, not
   enforced: a record built by a helper reports the helper's line.
7. **No flake outputs** for internal modules, and **no auto-discovery**.

## Consequences

### Positive

- A capability's system and home halves live together; toggling one flag
  removes both.
- File layout can change without touching any host.
- Consistent with REFACTOR.md: one evaluator domain per value, explicit
  lists, no exports.

### Negative

- An area file holding several features shares one parse: a syntax error in
  an off feature breaks the area (mitigated by `nix fmt`).
- An area's features share its file, so a large area is a long file; the
  spill rule (D3) bounds it. Where `desktop.niri` lives is
  `features/desktop.nix`, or its own file listed there; errors carry
  `file:line`.

### Neutral

- Migration is many moves; each must pass the derivation-identity gate, and
  ordering-only diffs must be proven with `drvs-sets` / `nix-diff`.

## Verification

- Spike: an unselected feature whose module `throw`s, and one referencing a
  missing package attribute, leave Sleipnir's evaluation untouched.
- Migration slices: `just drvs` identical, or an ordering-only diff that is
  explained.
