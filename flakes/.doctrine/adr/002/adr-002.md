# ADR-002: Features are plain data addressed by attribute path

## Context

Modules are organised by evaluation class today (`modules/nixos/`,
`modules/home/{shared,linux}/`, `darwin/`), so one capability (snooze, sway,
capsule) is split across directories and joined only by a flag name.

REFACTOR.md (completed) removed an earlier setup in which every leaf was a
flake-parts module, auto-discovered by `import-tree`, registering itself as
`flake.homeModules.<name>` / `nixosModules`. Its reasons:

| Removed | Reason |
|---|---|
| leaf files as flake-parts modules | two evaluator domains conflated in one tree; ceremony for local-only modules |
| `import-tree` auto-discovery | a "magic directory" rule plus a flake input |
| `flake.*Modules` exports | indirection with one internal consumer |
| `cliPackages` option matrix | options with zero consumers |

That history rejects Den's plumbing (auto-discovery, outputs, flake-parts as
the carrier). It does not reject Den's shape: one identity for a capability
across classes. A precedent for the shape already exists:
`modules/shared/cli/_packages/*.nix` return `{common, linuxHome,
linuxSystem}` from one file per category.

Module merge order matters: list options merge in reversed breadth-first
import order (MULTIHOST "Lessons"), so moving or reordering imports changes
derivations.

## Decision

1. **Shape.** A feature is plain data: `{ nixos?, darwin?, homeManager? }`,
   each an ordinary module (inline or a path), plus an optional `requires`,
   a list of `"<area>.<name>"` prerequisites (ADR-001 D4). No other key is
   allowed: a misspelt class key would otherwise drop that half silently. A
   feature value is never itself a module of any evaluator.
2. **Addressing.** Features are referenced by attribute path
   (`desktop.niri`), never by file path. The tree is two levels deep,
   `<area>.<name>`. `features/default.nix` lists the areas and each
   `features/<area>/default.nix` lists its features, both as written lists
   of `{ name; value; }` pairs. Area and feature names may not contain `.`,
   since paths are dot-joined.
3. **Granularity.** File size is a judgement: not a five-line wrapper, not a
   thousand lines. A file may hold several features of one area; a feature
   with assets or tests may be a directory. Re-splitting files never touches
   hosts.
4. **Exclusion boundary.** Descriptors (feature attrsets, their `enable`
   options, outer settings schemas) may be evaluated globally. Implementation
   modules and package expressions stay unforced when unselected. This
   isolates evaluation failures (missing package attributes, removed options,
   `throw`). It does not isolate parse errors in a file holding descriptors;
   `nix fmt` parses every file before evaluation. Resolver code must not
   traverse into implementation values; testing attribute presence is fine.
   Structural checks (names, descriptor key names, `requires` paths, and
   options declared at a feature's path) read every descriptor, selected or
   not, and fail every host. Reading key names and option declarations
   forces no class value, so the boundary holds.
5. **Projection order.** Selected features project in area-index list order,
   never `attrNames` order. Migration preserves existing order. No numeric
   priorities without a concrete need.
6. **Identity.** One selected entry per feature path, so duplicates cannot
   arise from selection. `_file` is set for error provenance only.
7. **No flake outputs** for internal modules, and **no auto-discovery**.

## Consequences

### Positive

- A capability's system and home halves live together; toggling one flag
  removes both.
- File layout can change without touching any host.
- Consistent with REFACTOR.md: one evaluator domain per value, explicit
  lists, no exports.

### Negative

- An area file holding several features shares one parse: a syntax error in
  an off feature breaks the area (mitigated by `nix fmt`).
- "Where does `desktop.niri` live?" needs the area index; acceptable, since
  the index is explicit.

### Neutral

- Migration is many moves; each must pass the derivation-identity gate, and
  ordering-only diffs must be proven with `drvs-sets` / `nix-diff`.

## Verification

- Spike: an unselected feature whose module `throw`s, and one referencing a
  missing package attribute, leave Sleipnir's evaluation untouched.
- Migration slices: `just drvs` identical, or an ordering-only diff that is
  explained.
