# ADR-001: Feature selection is resolved outside the module evaluations

## Context

The repo builds three independent evaluations per host: NixOS, standalone
Home Manager (Linux), and nix-darwin (with Home Manager embedded). They use
separate nixpkgs pins and activate separately (ADR-003), so an option declared
in one is invisible to the others.

Selection today is a set of boolean feature flags (`modules/features.nix`),
resolved once per host by `lib.evalModules` in `features.nix`, injected as
`specialArgs.features`, and used to gate `imports` in host files. Most flags
default to `true`, so defaults describe Sleipnir rather than a host that says
nothing, and much is unconditional (desktop apps in
`modules/home/linux/default.nix`, capsule, agents, personal tools).

The main driver is cheap toggling per rebuild: turn off sway, niri, KDE, qemu,
ROCm, Blender, and turn them back on later without surgery.

A survey of the repo (2026-10-15) found no `mkIf` on `config`, no `osConfig`,
no assertions; `specialArgs.features` is read only by host files and
`modules/home/linux/default.nix`. The dependency graph is shallow: desktop
base ← compositors; emacs → zmx; satan* (home) → postgresql (system);
capsule → network bits. Alternatives considered: a Den-style reference
closure (`includes` + `genericClosure`) and the `flake-aspects` library. Both
add a dependency graph the repo does not need, and neither supports a host
overriding a profile's choice as directly as typed options do.

## Decision

We will resolve feature selection outside the NixOS / Home Manager / darwin
evaluations, by evolving the existing typed resolver:

1. **Trace.** host → profile → feature → class module → option definitions.
2. **Unit of selection.** One `enable` option per feature. A feature is a
   capability toggled independently (niri independent of sway).
3. **Profiles** are modules in the outer evaluation that set overridable
   defaults (`mkDefault`). Hosts override them.
4. **Prerequisites** are checked against the final resolved selection. The
   resolver may default a prerequisite on for convenience, but an explicit
   `false` alongside its dependent is an error, never a silent repair.
   Private implementation dependencies are ordinary `imports` inside the
   feature.
5. **Validation is enforced.** `lib.evalModules` does not check assertions.
   The resolver declares `assertions` and refuses to return a selection while
   any fail. Every factory (NixOS, standalone HM, darwin) consumes that
   checked value, so a home-only build validates too. Validation proves
   configuration intent, not that a service is activated or healthy.
6. **Capability activation belongs in feature selection.** Downstream
   overrides tune selected capabilities and must not independently recreate
   excluded features. This is a convention: upstream options such as
   `services.postgresql.enable` exist whether or not our feature is selected,
   so it cannot be enforced.
7. **Behaviour-preserving migration first.** Moving to this mechanism keeps
   each host's current effective selection. Making defaults lean (MULTIHOST
   S7) is a separate, deliberate behaviour change.

`specialArgs.features` may remain where explicit context passing serves a
clear purpose, but downstream modules should not inspect the global selection
to make composition decisions.

## Consequences

### Positive

- One mechanism, already in the repo and already understood; no new library.
- Typing catches misspelled features; `mkDefault` / `mkForce` / derived
  defaults (`follows`) keep working.
- Selection, dependency checks and integration conditions live in one
  traceable place.

### Negative

- Declaring an `enable` option per feature means loading every feature
  descriptor, so descriptors must stay cheap and lazy (ADR-002).
- No automatic dependency expansion: a host selecting a feature must also
  select its prerequisites (or accept a resolver default).

### Neutral

- If a real need for graph composition appears, a reference closure can be
  added on top; the spike records what would trigger that.

## Verification

- Spike slice (snooze pilot) tests: profile default, host override off,
  prerequisite error on a home-only build, unchanged pins and activation.
- Every migration slice passes the derivation-identity gate (`just drvs`,
  `just drvs-sets`).
