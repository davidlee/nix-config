# ADR-004: Integrations and settings ownership

## Context

Features sometimes need to configure each other: a base desktop module writes
a portal preference into every compositor's portal section (`xdg.nix`); home
services need a system database. Features also need tunable values, and
adding every tunable to a central host schema recreates the coupling we are
removing.

Two evaluations exist per Linux host (ADR-003), so a module can read options
only within its own evaluation.

## Decision

**Integrations.**

1. Integrations may configure already-available capabilities through ordinary
   options: options declared by nixpkgs, Home Manager, or a feature that is
   always present within that evaluation.
2. Integrations whose applicability depends on feature selection are
   explicitly selected by the outer composition layer (ADR-001), after
   selection defaults and overrides have resolved and prerequisites have been
   validated. They never expand the selection.
3. They are written as visible conditionals in a composition file. No
   registry, rule engine or automatic discovery of integration files until a
   real case demands it.

**Settings.**

4. Values shared by system and home, or needed during composition, are typed
   options in the outer resolver. Fixed facts that are not tunables (an
   address, a path), and values a consumer outside the flake also needs, may
   instead be plain constants in one file that every consumer imports.
5. Values specific to a selected implementation are ordinary downstream
   options, owned by the feature that declares them, and set by a host
   override module passed to that evaluator. Setting a value for an option
   that is absent because its feature is unselected is an error, which is
   intended.
6. Selection and settings stay separate: setting a value never selects a
   feature.

## Consequences

### Positive

- Composition policy stays in one place; implementations don't inspect the
  global selection.
- Features own their schemas; no central host schema grows per feature.

### Negative

- Option 1 requires a small always-present option where a fan-out exists
  (e.g. a list of portal desktop identifiers that compositors append to).

### Neutral

- Upstream options exist regardless of selection; see ADR-001's convention
  on recreating excluded features.

## Verification

- Reviewed per slice: any new selection-dependent conditional lives in the
  composition layer.
