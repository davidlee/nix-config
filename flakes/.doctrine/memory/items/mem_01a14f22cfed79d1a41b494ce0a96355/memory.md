Two traps when a jail runs a binary built on the host outside Nix (e.g. `cargo install` doctrine):

1. **File binds go stale.** A bwrap bind of a single file pins one inode. `cargo install` writes a new file and renames it over the old one, so the jail keeps the deleted file. Hooks then fail with ENOENT until the jail restarts (doctrine IMP-249). Bind a *directory* instead: a renamed-in file shows up immediately. Give the binary its own install root so that directory holds nothing else (`cargo install --root ~/.local/share/doctrine`). Don't bind over `~/.cargo/bin`: that exposes every host cargo install and hides the jail's own persisted `~/.cargo`. Verify with a rename while a jail runs, not just launcher text.

2. **The store closure is missing.** jail-nix (`bind-nix-store-runtime-closure`) exposes only the jail's own closure. A cargo-built ELF links specific store paths (glibc `ld-linux`, gcc-lib via RUNPATH). Without them, `command -v` finds the binary but running it gives "command not found" (ENOENT from the interpreter). `elfClosureBinds` in `flakes/agents/jailed-agents.nix` binds interpreter + RUNPATH closure (`nix-store -qR` on the host) over `--args 23`. It runs at launch, so a reinstall built by a different toolchain needs a relaunch.

Current wiring: `hostDoctrine` (default on) binds `~/.local/share/doctrine/bin` at `/run/doctrine-bin` and prepends it to the jail PATH; the host PATH has the same dir ahead of `~/.cargo/bin` (`modules/nixos/env.nix`).
